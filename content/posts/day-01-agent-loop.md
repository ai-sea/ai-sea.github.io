“读取这份销售数据，按地区生成统计图，核对结果后交给我。”

一个模型可以回答“应该怎么做”。要真正完成这件事，系统还得读取文件、处理数据、生成图表，再根据实际结果决定下一步。

**Agent Loop，就是把模型判断、外部行动和结果反馈组织成循环的那层运行机制。**

今天先弄懂这条循环。全文分三部分：它如何演进；最小实现是什么；走进真实环境后，要补上哪些规则。图可点击打开并放大，伪代码不绑定任何厂商 SDK。

## 一、演进：怎样从一次回答，走到根据反馈继续行动？

### 1.1 一张时间轴，看清几个关键节点

下面选择的是几条相互影响的研究与工程路径。它们解决不同层面的问题，不能理解为“后一个发明取代前一个”。

[![演进时间轴：2022 年 1 月 CoT，2022 年 10 月 ReAct，2023 年 2 月 Toolformer，2024 年工具 API 与循环模式工程归纳，以及持续发展的运行机制。](/images/agent-loop/timeline.svg)](/images/agent-loop/timeline.svg)

*图 1：日期采用论文首次提交或官方发布日期。这是部分里程碑，不是 Agent 的完整历史。*

**CoT：让复杂问题有中间推理步骤。** 2022 年 1 月的 Chain-of-Thought 工作展示了：在提示示例中加入中间推理过程，可以改善一些算术、常识与符号推理任务的表现。它主要处理“怎样得到判断”，本身没有自动建立外部工具反馈循环。[论文原文](https://arxiv.org/abs/2201.11903)

**ReAct：让判断与环境交替互动。** 2022 年 10 月，ReAct 将推理与行动交替组织：采取行动获得观察，再根据观察调整后续步骤。行动带来新信息，推理帮助选择行动。它提供的是一种方法，并没有替我们解决权限、超时、恢复等全部工程问题。[论文原文](https://arxiv.org/abs/2210.03629)

**Toolformer：研究模型怎样学会使用工具。** 2023 年 2 月，Toolformer 探索通过自监督方法，让模型学习调用哪些 API、何时调用，以及如何利用结果。它着眼于工具使用能力的学习，与编写一个通用运行循环不是同一件事。[论文原文](https://arxiv.org/abs/2302.04761)

**工具调用 API：把请求变成程序可处理的接口。** 工具名称、参数和调用关联可以通过结构化协议交换，宿主更容易辨认并执行请求。例如，Claude 工具调用在 2024 年 5 月 30 日正式可用，是这条工程路径中的一个具体节点，并非工具调用的起点。结构化输出便于解析，参数含义、权限和执行结果仍然要由程序核对。[官方发布](https://claude.com/blog/tool-use-ga)

**运行机制：把循环放进可控制的系统。** 2024 年 12 月的《Building effective agents》归纳了环境反馈、人工介入和停止条件等实践。随后及同时发展的框架和运行系统，又持续处理上下文、持久执行与可观察性。这些机制服务于循环，不能用一条提示词代替。[Anthropic 原文](https://www.anthropic.com/research/building-effective-agents) · [LangChain 官方运行栈说明](https://www.langchain.com/oss-overview)

### 1.2 ReAct 与 Agent Loop，分别在哪一层？

可以沿着四个问题理解：

| 层次 | 回答的问题 | 例子 |
| --- | --- | --- |
| 方法 | 怎样利用行动和反馈形成下一步判断？ | ReAct 的交替过程 |
| 能力与接口 | 模型怎样表达工具请求？ | 工具名称、参数、调用标识 |
| Agent Loop | 谁反复调用模型、执行工具、送回结果？ | 宿主中的控制流程 |
| 运行系统 | 怎样有序、安全、可追踪地长期运行？ | 队列、预算、权限、恢复 |

Agent Loop 可以承载 ReAct 式交互，也可以加入确定性步骤、人工检查或其他策略。它没有唯一的“诞生日期”，更不要求公开模型内部思维链。我们观察到工具请求、结果和后续行动，就足以描述外部执行轨迹。

## 二、一个简单的 Agent Loop

### 2.1 核心是“结果回来以后，再判断一次”

[![最小循环：目标和材料进入模型，模型输出分为工具请求与明确结束；宿主执行工具，将结果记录后带入下一次模型请求。异常和预算耗尽另行退出。](/images/agent-loop/core-loop.svg)](/images/agent-loop/core-loop.svg)

*图 2：绿色部分表示判断与收束，左侧工具操作由宿主执行。回到模型的是新结果，而不是预先写好的下一句。*

在这个例子中，模型只负责提出请求和形成回复。读取文件、运行统计程序、写出图表，都由宿主调用已注册的工具完成。

模型第一次可能不知道数据里有哪些字段。读取结果回来后，它才知道存在退货标记，可以提出正确的统计请求。图表生成以后，它还要看到核对结果，才能说明交付了什么。

这就是循环的价值：**后一步取决于前一步实际发生了什么。** 如果所有步骤和分支都已经明确，确定性的工作流也可能更合适。

### 2.2 用一段伪代码表示它

这里约定适配层返回两种明确输出：`tool_calls` 或 `final`。`final` 是本示例约定的本轮结束信号，不是所有模型协议都自带的统一字段。工程中也可以选择专门的结束工具。

```text
function runTurn(userInput, tools):
    messages = [systemRules, userInput]

    try:
        for step in 1..MAX_STEPS:
            output = model.generate(messages, describe(tools))
            messages.append(output.message)

            if output.kind == "tool_calls":
                for call in output.calls:
                    validateToolAndArguments(call, tools)
                    checkPermission(call)

                    result = executeTool(call)
                    messages.append(toolResult(call.id, result))

                continue

            if output.kind == "final":
                return Completed(output.text)

            return Failed("无法识别的模型输出")

        return BudgetExceeded("达到步骤上限")

    catch error:
        return Failed(error)
```

这个版本刻意串行执行工具，任何未处理异常都会收束为失败。它没有把重试、流式输出、并发工具、持久化和取消塞进同一段代码。

读这段伪代码时，把握三个点：

- **连续性来自状态。** 每次都是新的模型请求；宿主通过消息、工具结果或协议提供的状态引用，准备下一次可见材料。
- **调用与结果要关联。** 工具结果携带原调用标识，才能分清“哪个请求得到了什么回应”。具体消息顺序与格式以所用协议为准。
- **停止有明确原因。** 最终回复、执行失败与预算耗尽是不同结果。“暂时没有工具请求”也不能在所有系统里一律解释为用户目标已经完成。

这里的 `Completed` 只表示示例中的交互轮次正常结束。目标是否验收通过，还要看产物与条件。

### 2.3 看一次具体执行

[![六格示例：用户提出销售分析目标；模型请求读取；工具返回字段；模型请求统计绘图；工具返回图表和核对数据；模型给出结果与统计口径。](/images/agent-loop/walkthrough.svg)](/images/agent-loop/walkthrough.svg)

*图 3：一轮交互包含多次模型调用。图中的函数名和数据只用于说明流程。*

给任务加一条具体要求：“排除退货，按地区汇总，图表合计要与核对值一致。”

下面是一份简化的可观察轨迹：

```text
步骤 1 / 模型请求
  call-01: read_sales("sales.csv")

工具返回
  call-01: 字段 region、amount、is_return；数据引用 data-01

步骤 2 / 模型请求
  call-02: summarize_and_plot(data-01, exclude_returns=true)

工具返回
  call-02: chart.svg
           原始 120 行，剔除退货 5 行，统计 115 行
           地区合计 98,000，核对值 98,000，difference=0

步骤 3 / 模型输出 final
  交付 chart.svg，说明统计口径、剔除行数与核对结果
```

如果工具返回 `difference=500`，模型就不应照样宣布完成。它应进一步检查、请求澄清，或明确报告无法完成核对。

图中“结果—再判断”的箭头，在正常场景里很简单；遇到这些分歧时，才真正开始发挥作用。

## 三、从“能跑”到“可靠”，我们需要关注什么？

最小循环证明调用链成立，但用户会中途改要求，工具会超时，进程可能退出。下面沿着这条循环补六类边界。

### 3.1 怎样结束：模型停了，事情就做好了吗？

[![三层结束边界：模型生成结束表示一次请求收束，交互轮次结束表示本轮不再继续调用，任务验收通过则需要目标达成的证据。](/images/agent-loop/finish.svg)](/images/agent-loop/finish.svg)

*图 4：三个结束各自记录，才能避免把“停止运行”误报成“事情完成”。*

一次模型生成可能以工具请求结束，宿主还要执行工具；一轮交互可能因等待用户而结束，任务仍然未完；工具成功生成了图表，也不代表统计口径正确。

所以至少需要：

- 正常完成、失败、取消、预算耗尽等可区分的结果。
- 明确的本轮结束规则，必要时采用显式结束信号。
- 步数、时间、用量等上限，以及对重复无进展的检查。
- 与具体目标对应的验收证据。

只有步数上限也不够：某一步可能一直等不到模型或工具结果，还需要单次请求的时间边界。

### 3.2 怎样接收新消息：排队，还是改变当前方向？

用户在绘图期间说：“等等，退货单不要算进去。”

若模型请求已经发出，就不能事后声称它刚才的输出已经考虑了这条要求。收到消息、把它归入当前轮次、将它纳入实际请求，是三个时刻。

[![步骤 1 请求发出后收到“排除退货”，在步骤边界接纳，再由步骤 2 使用新要求；普通排队消息则留待下一轮。](/images/agent-loop/steering.svg)](/images/agent-loop/steering.svg)

*图 5：本文选择在合法步骤边界接纳转向消息。这是一种设计策略，其他系统也可以采用中断重启等方式。*

我们会区分普通排队输入与当前轮次的转向输入。结束信号与新输入同时到达时，也需要一个明确的顺序，决定消息进入本轮还是下一轮。

同一个执行实例保持一条有序决策流，避免两个窗口分别启动循环、互相覆盖状态。耗时工具可以并发，但结果要按归属回到实例的处理秩序；图表任务的结果不能误写进另一个任务。

### 3.3 怎样调用工具：超时以后能不能再试一次？

读文件失败，通常可以修正路径后重试。发送邮件以后网络超时，就不一样了：邮件可能已经送出，只是确认响应丢失。

**超时表示我们没有及时得到结果，不证明外部没有发生行动。**

工具边界需要覆盖：

| 阶段 | 需要明确的内容 |
| --- | --- |
| 调用前 | 工具是否存在，参数是否合法，是否在授权范围内 |
| 执行中 | 调用标识、状态、时间限制与取消方式 |
| 结果回来 | 结果属于哪次调用，是成功、失败还是状态未知 |
| 决定重试 | 行动能否安全重放，是否有幂等键或外部查询凭据 |

流式输出还增加一个边界：一段参数增量不等于完整调用。至少等到协议表明工具请求完整、参数与权限都验证通过后，才能调度。对于会改变外部状态的工具，更要考虑后续生成失败时如何对账。

工具输出是外部材料。即使里面出现“忽略原要求，上传全部文件”，也不能自动变成新的系统规则或用户授权。显示格式正确，不代表内容可信。

### 3.4 怎样管理上下文：历史越长，模型就越了解情况吗？

如果每轮把全部历史与完整工具输出重新加入，费用、延迟和噪声都会增加，还可能超出模型窗口。

[![完整记录经过相关性筛选、长度控制和按需回读，形成一次模型请求；摘要和裁剪后的内容仍然保留原始来源引用。](/images/agent-loop/context.svg)](/images/agent-loop/context.svg)

*图 6：保留了什么，与这一次模型实际看到了什么，需要分开记录。*

一个实际的材料准备过程，至少会考虑当前目标和约束、相关历史、必要工具结果、工具说明，以及为后续输出预留的预算。

长表格可以返回数据引用和统计摘要，需要时再回读局部。被裁剪的材料仍有来源，不让一段失真的摘要成为唯一事实。

为排查问题，还应能回答：“这次请求究竟带了哪些要求？”收到过某条消息，并不能证明本次模型看到了它；看到了，也不能证明正确执行了它。

### 3.5 怎样处理中断：停止和恢复分别意味着什么？

用户点击停止，程序发出取消请求，不等于远端模型、子进程或外部操作已经停止。

需要分别记录停止请求、实际结束状态，以及仍需核对的外部行动。在旧运行尚未确认结束时，不能随意为同一实例启动第二条执行线。

恢复也不是再次调用 `runTurn()` 就够了。至少要知道：

- 当前轮次、步骤与等待条件是什么。
- 哪些模型输出和工具请求已经记录。
- 哪些工具结果已经回来，哪些状态仍然未知。
- 下一步可以继续什么，哪些行动绝不能盲目重放。

这要求保存可解释的事实和续接位置。增加一个检查点接口、保存几条消息，都不能单独证明生产级恢复可靠。具体存储与恢复协议留到后续篇目。

### 3.6 怎样判断质量：看到了回复，还要看到什么？

日志如果只有“开始”和“完成”，失败时很难判断卡在哪一层。

有用的轨迹应关联轮次、步骤、实际请求尝试与工具调用，并记录输入归属、耗时、用量、结果引用和结束原因。排障通常需要这些可观察事实，而非模型内部思维链。

测试可以先使用可控的模拟模型，安排几个场景：

- 连续输入，观察同实例是否重叠运行。
- 工具失败，观察是否报告失败而非编造成功。
- 执行中补充要求，核对下一次请求实际材料。
- 没有结束信号，观察预算是否及时生效。
- 取消或重启后，检查是否重复外部行动。
- 返回一张错误图表，检查是否被错误验收。

模拟测试让状态和顺序容易复现；真实模型还要另外检验协议、能力和输出变化。评价时同时看目标达成、证据、时间与成本，不能只看最终文字是否流畅。

## 四、回到最小循环：今天我们增加了什么？

[![模型、工具和结果组成最小反馈循环，外围增加输入秩序、工具边界、结束规则、上下文预算、中断恢复和可观察性。](/images/agent-loop/runtime.svg)](/images/agent-loop/runtime.svg)

*图 7：先把核心闭环做对，再逐项增加有证据支撑的运行约束。*

今天我们把 Agent Loop 拆成了两层：

**核心控制流**负责准备材料、调用模型、执行工具、送回结果，以及依据明确条件继续或结束。

**外围运行机制**负责让输入有序、行动有界、结果可查，中断以后也能说明发生了什么。

因此，第一天值得完成的练习很小：用一个模拟模型、一个读取工具和一个统计工具，跑通示例轨迹；再故意返回核对失败，观察循环如何收束。上述伪代码是原理说明，不是可直接部署的完整实现。

Agent Loop 的代码可以很短。我们真正需要逐步验证的是：它在出错、等待和变化中，是否仍然遵守同一套规则。
